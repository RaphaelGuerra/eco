# Story 1.2: Dynamic Environment System

## Status
Ready for Development

## Story
**As a** player,
**I want** the in-game time and weather to change automatically,
**so that** the world feels dynamic and alive.

## Acceptance Criteria
1. The `gameTime` state variable cycles between 'day' and 'night' every 30 seconds.
2. The `weather` state variable cycles between 'clear' and 'rainy' every 30 seconds.
3. The status panel display correctly updates to reflect the current `gameTime` and `weather`.

## Dev Notes

### Previous Story Insights
Story 1.1 established the foundational UI layer with static time and weather display. This story builds upon that foundation by making the environment dynamic and responsive to automatic changes.

**Key dependencies from Story 1.1:**
- GameContext with gameTime and weather state properties
- StatusPanelContainer component for displaying environment information
- TimeOfDay and WeatherCondition enums
- Basic state management patterns with useReducer

### Architecture Context
This story enhances the State Management Layer and introduces a new Service Layer component for environment cycling logic. The environment system will be a core service that other game systems can depend on for time/weather-aware behavior.

**Architecture Impact:**
- Extends GameContext with environment cycling actions
- Introduces EnvironmentService for timer management
- Enhances StatusPanelContainer with real-time updates
- Prepares foundation for environment-based encounter mechanics (Story 1.4)

[Source: docs/architecture/high-level-architecture.md#internal-architecture-diagram]

### Data Models
Building upon the existing data models from Story 1.1:

**Enhanced GameState Interface:**
```typescript
interface GameState {
  currentLocationId: string;
  gameTime: TimeOfDay; // 'day' | 'night' - now dynamically changing
  weather: WeatherCondition; // 'clear' | 'rainy' - now dynamically changing
  lastEncounterTime: number;
  activeFieldResearch: ActiveFieldResearch | null;
  researchFocus: ResearchFocus;
  environmentCycling: {
    isActive: boolean;
    lastUpdate: number;
    timeInterval: number; // 30000ms = 30 seconds
    weatherInterval: number; // 30000ms = 30 seconds
  };
}
```

**New Environment Actions:**
```typescript
type GameAction = 
  | { type: 'SET_TIME'; payload: TimeOfDay }
  | { type: 'SET_WEATHER'; payload: WeatherCondition }
  | { type: 'CYCLE_TIME' }
  | { type: 'CYCLE_WEATHER' }
  | { type: 'TOGGLE_ENVIRONMENT_CYCLING'; payload: boolean }
  | { type: 'SET_ENVIRONMENT_INTERVALS'; payload: { timeInterval?: number; weatherInterval?: number } };
```

[Source: docs/architecture/high-level-architecture.md#data-models]

### State Management Pattern
Extending the existing React Context + useReducer pattern with:

- Service layer integration for timer management

### Technical Constraints
- React 18.2.x with TypeScript 5.4.x
- Vite 5.2.x for build tooling
- Tailwind CSS + CSS Modules for styling
- Component-based architecture with clear separation of concerns
- Performance requirement: Environment updates must not impact UI responsiveness

[Source: docs/architecture/high-level-architecture.md#tech-stack]

### Implementation Notes
- Use setInterval for environment cycling with proper cleanup
- Implement smooth visual transitions for environment changes
- Add pause/resume functionality for testing and user control
- Ensure proper memory management to prevent memory leaks
- Optimize re-rendering to maintain 60fps performance
- Add visual feedback for environment transitions (subtle animations)

### Performance Considerations
- Environment cycling should not impact encounter calculation performance
- Timer cleanup is critical to prevent memory leaks
- Visual transitions should be lightweight and non-blocking
- State updates should be batched when possible

### Project Structure Notes
The application follows a layered architecture with:
- Component Layer (UI) - React components with real-time updates
- Service Layer - Environment cycling logic (new)
- State Management Layer - Enhanced useReducer/Context
- Persistence Layer - localStorage (environment state persistence)

[Source: docs/architecture/high-level-architecture.md#internal-architecture-diagram]

## Testing

### Unit Test Requirements
- `EnvironmentService.test.ts`: Test timer management and cycling logic
- `useEnvironmentCycling.test.ts`: Test hook integration and cleanup
- `GameContext.test.tsx`: Test new environment actions and state updates
- `StatusPanelContainer.test.tsx`: Test real-time updates and transitions

### Test Scenarios
1. Environment cycling occurs at correct intervals (30 seconds)
2. Time and weather cycle through all valid states
3. Status panel updates immediately when environment changes
4. Environment cycling can be paused and resumed
5. Proper cleanup occurs when components unmount
6. Performance remains stable during continuous cycling
7. State persistence works correctly with environment cycling

### Testing Standards
- Unit tests using Vitest & React Testing Library
- Tests should be co-located with component files
- Target >90% code coverage for core services
- Test file location: Same directory as component with `.test.tsx` extension
- Performance testing for timer management and UI updates

### Accessibility Testing
- Verify screen reader compatibility with dynamic content
- Test keyboard navigation during environment changes
- Ensure sufficient color contrast during transitions
- Validate semantic HTML structure with dynamic updates
